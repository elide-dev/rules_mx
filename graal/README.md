# Building upstream GraalVM

Bazel fetches a checksum-pinned Oracle source archive and applies the BUILD files generated by mx and Gazelle. Builds and tests use declared sources and toolchains. A local Graal checkout is optional. The three suites share one external repository so cross-suite edges use ordinary Bazel labels. [Pinned Oracle source tree](https://github.com/oracle/graal/tree/7b7825ae92c83d91bb20d76bc64b68b344449cf3)

```sh
bazelisk test --config=elide-processors //graal/... @graal//sdk/... @graal//truffle/... @graal//compiler/...
bazelisk query 'tests(//graal:sdk_tests)'
bazelisk test @graal//sdk:org.graalvm.word.test.org.graalvm.word.test.WordTests
bazelisk query 'somepath(@graal//truffle:com.oracle.truffle.api.library, @graal//sdk:POLYGLOT)'
tools/buildbuddy test --config=buildbuddy-rbe --config=elide-processors //graal/... @graal//sdk/... @graal//truffle/... @graal//compiler/...
```

Runtime tests verify packaged version resources, JPMS module loading and JLine provider selection on JDK 21 and Labs JDK 25. |
| Truffle | 53 of 69 declared projects, including JNI attach, host interop, SimpleLanguage and NFI with its libffi backend. The SDK and Truffle slice generally targets Java 21. Shaded libraries compile at their declared releases, including the JDK 22 JLine overlay. Some SDK projects declare an older minimum while using newer APIs, including `java.io.Serial`. The libgraal API compiles as one unit because its packages depend on each other. Gazelle keeps project resources, processors and tests with their owning compilations and splits eligible source-only projects by package.

`--classpath-dists` follows same-suite distribution dependencies during Gazelle export. `mx_classpath_dist` exposes their constituent jars and combined JavaInfo. Platform-independent file layouts support literal contents and exact file references to another layout. The SDK version layouts exercise both operations. Select individual distributions for JAR assembly and JPMS descriptors with `--archive-dist DIST`. The Native Bridge closure uses this path. JAR assembly supports release-specific class overlays and compiles their JPMS descriptors against the classes visible at each release. Signing and publication remain separate migration work.

Truffle's eight declared processors run on the execution platform. Its DSL processor inspects javac internals that Turbine does not implement. The generator selects `--javac-only-processor truffle:TRUFFLE_DSL_PROCESSOR` for that distribution. Bazel runs javac once on affected projects, then extracts an interface jar containing the generated types for downstream compilation. Eligible Elide compilations keep their worker and ABI settings. For selected pinned Truffle projects the generator sets individual Error Prone checks to warning severity. Stock JavaBuilder reports the upstream diagnostics, including an unconditional recursive call in instrumentation’s `NearestNodesCollector`.

## Run SimpleLanguage

```sh
printf 'function main() { println(6 * 7); }\n' | bazelisk run @graal//truffle:sl -- --disable-launcher-output
bazelisk run --config=labsjdk @graal//truffle:sl -- path/to/program.sl
bazelisk query 'filter("sl[.]test[.]", tests(@graal//truffle/...))'
bazelisk test --config=elide-processors @graal//truffle:sl.test.Fibonacci @graal//truffle:sl.test.error.InvalidBreak
```

The launcher resolves its module path from the Bazel-built distributions and runs on the selected JDK. Each guest test checks upstream output or diagnostics with both values of `sl.UseBytecode`. Tests extract the JNI attach library into Bazel's test temporary directory and fail if loading it fails. The `sl` launcher uses the interpreter. Use `sl_jit` to select the Labs JDK and run with the source-built Graal compiler on its upgrade module path.

```sh
bazelisk build --config=elide-processors @graal//compiler:GRAAL
bazelisk run --config=elide-processors @graal//compiler:sl_jit -- path/to/program.sl
bazelisk test --config=elide-processors @graal//compiler:sl_compilation_test
```

The compiler requires Labs JDK 25.0.4.1.1+1 with JVMCI 25.4-b23, as specified in the pinned Graal tree. JavaBuilder uses that JDK for projects importing concealed JVMCI APIs, with strict dependencies, annotation processing and ABI extraction. Four upstream compiler diagnostics are reported as warnings. The distribution merges generated service providers and option descriptors into its JPMS descriptor. The compiled guest test also verifies the file origin of the loaded compiler module.

The archive action consumes Truffle registration markers, filters documentation snippets using the suite pattern, and assembles the Java 9 and 21 overlays. The pinned mx includes a fix for repeated module descriptor rendering so both releases retain singleton qualified exports and service providers.

## Run upstream JUnit tests

```sh
bazelisk query 'filter("sl_jit[.]tck[.]", tests(@graal//truffle/...))'
bazelisk test --config=elide-processors @graal//truffle:sl_jit.tck.IdentityFunctionTest
bazelisk test --config=elide-processors @graal//truffle:com.oracle.truffle.sl.test.com.oracle.truffle.sl.test.SLTestSuiteBytecodeCached
bazelisk test --config=elide-processors @graal//compiler:GR35581Test @graal//compiler:GR36613Test @graal//compiler:GR42688Test @graal//compiler:TruffleDirectCallNodeTest
```

Each JUnit label supports Bazel test filtering and writes JUnit XML. The TCK loads the SL provider from its distribution JAR and requires it through `-Dtck.language=sl`. At this source pin the TCK reports 16,564 cases per runtime. SL supplies no inline snippets, so `InlineExecutionTest` has zero cases. The SL JUnit suite reports 685 cases, including the 57 upstream programs in each of its four runner configurations.

## Truffle and compiler test distributions

```sh
bazelisk build --config=elide-processors @graal//truffle:TRUFFLE_TEST @graal//compiler:GRAAL_TEST
bazelisk test --config=elide-processors @graal//truffle:harness_tests @graal//compiler:harness_tests
bazelisk test --config=elide-processors @graal//compiler:jdk.graal.compiler.test.jdk.graal.compiler.annotation.test.TestAnnotationsOnTypes
bazelisk query 'kind(".*_test rule", filter("jdk[.]graal[.]compiler[.]test[.]jdk", @graal//compiler:*))'
```

Gazelle emits 570 Truffle and 1,678 compiler JUnit class targets from the new projects. CI runs all discovered classes in the DSL, library, bytecode, debugger, object and static-object projects, plus selected API, instrumentation, string and sandbox tests. The compiler selection exercises code generation, annotation evolution, vector-module loading, subprocesses and four SL compilation configurations. Choose any other generated class explicitly by label. The class targets carry the Bazel `manual` tag so the two explicit suites determine the default workload. Qualification of the remaining classes is ongoing.

The shared compiler launcher puts the source-built `GRAAL` on the Labs JDK upgrade module path. It replaces `GRAAL_TEST_COMPILETIME` with `GRAAL_TEST_RUNTIME` on the test classpath and uses mx's JUnit module support for package access and test annotations. A small Java launcher reads the Bazel test environment and passes the exact Java command and target-platform HSDIS library to the upstream subprocess harness. This also works with the released Elide Python overlay, which preserves the native process environment when launching Java. The ten Truffle test projects share the packaged `TRUFFLE_TEST` classpath, including the shaded JCodings implementation and encoding tables.

Production and test Java compilations preserve method parameter names as mx does. The compiler regression corpus uses Labs javac with its Graal and Truffle processors and the upstream Java 24 source level. Error Prone checks are disabled on this test project because it intentionally contains pathological programs.

## SDK launchers and toolchain tests

```sh
bazelisk build --config=elide-processors @graal//sdk:JLINE3 @graal//sdk:LAUNCHER_COMMON
bazelisk test --config=elide-processors @graal//sdk:org.graalvm.launcher.test.org.graalvm.launcher.test.LauncherTest @graal//sdk:org.graalvm.toolchain.test
bazelisk test //graal:launcher_modules_test
bazelisk test --config=labsjdk //graal:launcher_modules_test
```

The SDK graph binds the published JLine binary and source archives by the SHA-512 digests in the pinned suite. Separate actions relocate the sources and resources, apply Graal's patches, compile the base and JDK 22 projects, and assemble the multi-release JAR. The launcher module test loads the exec provider on JDK 21 and additionally loads the foreign-function provider on Labs JDK 25. The C and C++ probes compile the upstream sources with the registered Elide LLVM toolchain and run both binaries, checking their output.

## Native Bridge

```sh
bazelisk build --config=elide-processors @graal//sdk:NATIVEBRIDGE @graal//sdk:NATIVEBRIDGE_LAUNCHER_RESOURCES
bazelisk test --config=elide-processors //graal/nativebridge/... //graal/nativebridge:native_isolate_test
tools/buildbuddy test --config=buildbuddy-rbe --config=native-image-linux //graal/nativebridge:native_isolate_test
bazelisk run --config=elide-processors //graal/nativebridge:benchmark -- external-isolation
```

The archive action uses mx's resolved membership, consumes the processor's JNI markers and merges their providers with ordinary service files. The execution JDK compiles the JPMS descriptors against the packaged dependencies. A module-layer test loads both providers through Java's ServiceLoader. The upstream test project checks expected processor diagnostics during compilation and runs the 18 methods in `BinaryOutputTest`.

The launcher uses the target JDK's JNI headers, the registered C++ toolchain and mx's OS-specific flags. Its resource target exposes the executable at `<os>/<arch>/launcher`. The round-trip tests use the upstream benchmark's generated factory and service implementation. They exercise a child JVM and a Native Image shared library, including in-process and cross-process calls, reference passing and marshalling. The shared library uses the registered Elide Native Image toolchain. Linux AMD64 CI runs this test in the existing Native Image step. macOS ARM64 uses the same targets. Other target platforms require compatible toolchains and separate qualification.

The benchmark accepts `no-isolation`, `internal-isolation` and `external-isolation`. Omitting the mode runs all three. The pinned benchmark includes a timing patch so a batch shorter than one millisecond still reports throughput.

## Truffle NFI

Bazel compiles the mx-pinned libffi 3.4.8 sources with the Elide C/C++ toolchain and links them into Truffle’s JNI library. The backend JAR contains the shared library, platform file list and hash that Truffle uses to extract it. The upstream tests receive their two fixture libraries through the declared `TRUFFLE_TEST_NATIVE` directory. Each JUnit class has its own target, including the callback round trip.

```sh
bazelisk build --config=elide-processors @graal//truffle:TRUFFLE_NFI_LIBFFI @graal//truffle:TRUFFLE_TEST_NATIVE
bazelisk test --config=elide-processors @graal//truffle:com.oracle.truffle.nfi.test.com.oracle.truffle.nfi.test.GlobalNFITest
```

## Extending the graph

Run `tools/generate-graal --check` to reproduce the checked-in patches from the pinned archive. Add suite roots and external dependency bindings to `tools/generate-graal`, regenerate, and inspect the BUILD diff. To try an upstream revision before changing the pin, pass a checkout path to the generator. Make the archive pin, patches and regression tests part of the same change.

| Next checkpoint | Acceptance under Bazel |
| --- | --- |
| SDK toolchain distributions | Assemble the five LLVM, Ninja, CMake and musl redistribution layouts with their upstream contents and platform filters. Their packaged payloads are separate from the Elide LLVM toolchain used for Bazel compilation. |
| Complete Truffle | Extend default execution to the remaining API, instrumentation, string and sandbox tests. Migrate the Panama NFI backend and its JDK 22 overlay. |
| Compiler and SubstrateVM | Qualify more classes from the full compiler distribution, including architecture-specific backends and VM-specific test configurations. Build the required Espresso Shared dependencies and SubstrateVM, then produce and execute an image with the newly built toolchain. |
| Languages and tools | Migrate Regex, Sulong, Wasm, Espresso, Espresso Compiler Stub, Tools, Visualizer, Web Image and Sandbox Toolchains with their Java, native and external inputs. Run each suite's upstream tests. |
| VM assembly | Pin the external components required by each selected VM configuration. Assemble the distribution and run its launchers, component tests and corresponding mx gate equivalents from a clean Linux RBE build. |

The migration is complete when the selected GraalVM distributions can be built from source, their upstream test gates run, and their packaging and runtime behavior match the reference mx builds. Building the Java Native Image API or using an existing Native Image executable covers only part of that work.
