# Building GraalVM

Bazel fetches a checksum-pinned Graal source archive, by default the Elide fork, and applies the BUILD files generated by mx and Gazelle. Builds and tests use declared sources and toolchains. A local Graal checkout is optional. The suites share one external repository so cross-suite edges use ordinary Bazel labels. [Pinned source tree](https://github.com/elide-dev/graal/tree/21dea4deb60d8aa9b07cbd3cc77b1581b61b6fb2) (`elide-dev/graal` `elide-25.6.x`, based on `oracle/graal@7b7825ae92c`)

```sh
bazelisk test --config=elide-processors //graal/... @graal//sdk/... @graal//truffle/... @graal//compiler/...
bazelisk query 'tests(//graal:sdk_tests)'
bazelisk test @graal//sdk:org.graalvm.word.test.org.graalvm.word.test.WordTests
bazelisk query 'somepath(@graal//truffle:com.oracle.truffle.api.library, @graal//sdk:POLYGLOT)'
tools/buildbuddy test --config=buildbuddy-rbe --config=elide-processors //graal/... @graal//sdk/... @graal//truffle/... @graal//compiler/...
```

## Work on sibling checkouts

Use `tools/graal-dev` from the `rules_mx` checkout. It looks for a sibling `graal` checkout and optional `graaljs` and `graalpython` checkouts. If your source checkouts live in a separate parent directory, pass it with `--workspace`.

```sh
tools/graal-dev test --config=elide-processors @graal//sdk:org.graalvm.word.test.org.graalvm.word.test.WordTests
tools/graal-dev run --config=elide-processors @graal//graal-js:js -- -e 'print(6 * 7)'
tools/graal-dev test --config=elide-processors @graal//graal-js:regression/direct_eval
tools/graal-dev run --config=elide-processors --config=labsjdk @graal//graalpython:python -- -c 'import sys; print(sys.version)'
tools/graal-dev test --config=elide-processors --config=labsjdk @graal//graalpython:zlib/ChecksumTestCase.test_crc32start
```

Use a reverse-dependency query to select tests from the packages and targets you want to check. This example finds GraalJS regressions and the Truffle SimpleLanguage Fibonacci test affected by an edit to the Truffle API.

```sh
tools/graal-dev query 'kind(".*_test rule", rdeps(@graal//graal-js:all + @graal//truffle:sl.test.Fibonacci, @graal//truffle:com.oracle.truffle.api))'
```

The command generates the local BUILD overlays from mx and Gazelle and symlinks source files into the same Bazel repository. Edits to existing sources are visible to Bazel immediately. Adding, removing, or renaming a file and changing mx suite metadata refresh the generated graph. Use `--sync` after changing Java imports or other source content that changes Gazelle’s dependency analysis. The checkouts need to match the Bazel input pins in `rules_mx`. CI qualifies Graal at `21dea4d`, GraalJS at `747d45b`, and GraalPy at `11344f3`.

The live GraalPy launcher uses Labs JDK 25 and bundles the standard library, GraalPy core library, headers, platform versions, and source-built zlib. The first two upstream zlib checks are individually selectable.

Build `@graal//graalpython:GRAALPY_JVM_STANDALONE_RELEASE_ARCHIVE` with `--config=elide-processors --config=labsjdk` for an installable tarball. It bundles the pinned JDK, package-relative launchers, frozen bytecode from the upstream freezer, native POSIX and zlib support, and the C API extensions built with the upstream CMake project. The installed launcher uses the bundled runtime in the `jvm/` and `modules/` directories. `@graal//graalpython:jvm_standalone_test` extracts the archive into a path containing spaces and tests frozen imports, native modules, and upstream zlib checks.

The JVM archive uses a classpath launcher and compiles from the checked-in PEG parser. Native Image and GraalOS standalones, native bzip2 and LZMA, and the virtualenv seeder remain separate work.

Pass `--buildbuddy` before the Bazel command to use the existing BuildBuddy wrapper. The generated repository lives under `.graal-dev/` or the path supplied by `--state-dir`.

## Build the native toolchain launchers

Gazelle gets the Native Image main class, ordered classpath, module path and image options from the mx build task. Each image has its own Bazel target. The Bazel compilation mode controls debug information, so Linux and macOS generate the same overlay. Tool distributions expose individual files and preserve the aliases specified by mx when embedded in another archive. For discovery, Bazel fetches the LLVM and musl suite definitions at the revisions imported by Sandbox Toolchains. The JVM launcher distributions bundle the target Labs JDK and their ordered JARs alongside the executable. They can run after extraction without Bazel runfiles or a system JDK. The patched LLVM, musl and Rust bootstraps still need build rules.

The Espresso, Sulong and Wasm thin launchers use the SDK’s C++ JNI launcher. Gazelle gets the main module, Java class and installation paths from mx. Bazel compiles each executable with the registered C++ toolchain on Linux or macOS. The Wasm JVM standalone installs the JARs from mx’s resolved runtime classpath and a digest-pinned Labs JDK filtered by the upstream layout. The native standalone installs the source-built language library. Both use the release metadata of that JDK, matching an explicit mx `STANDALONE_JAVA_HOME`. CI unpacks each release archive and runs a guest with its installed launcher. The archive targets are addressable by both their suite declaration and their JDK-specific mx distribution name.

```sh
bazelisk query 'deps(@graal//sandbox-toolchains:SANDBOXED_MUSL_TOOLS_SWCFI, 2)'
tools/buildbuddy build --config=buildbuddy-rbe --config=source-native-image @graal//sulong:SULONG_NATIVE_TOOLS
tools/buildbuddy test --config=buildbuddy-rbe --config=source-native-image //graal:sandbox_launcher_test //graal:wasm_native_release_test //graal:wasm_jvm_release_test
tools/buildbuddy test --config=buildbuddy-rbe --config=labsjdk --config=elide-processors //graal:wasm_thin_launcher_test
```

The Wasm core JUnit launcher runs the source-built Graal compiler and Truffle runtime on the pinned Labs JDK. Bazel builds WABT 1.0.42 from the upstream source archive using the BCR’s native C++ targets. The tool accepts mx’s explicit feature flags, including features enabled by default in that release.

Sulong’s macOS bootstrap compiler uses the SDK declared by the Elide C/C++ toolchain. With Xcode 27 installed, select a compatible SDK such as macOS 26.4 through `SDKROOT` or a checksum-pinned `llvm.darwin_sdk` archive. The pinned Sulong linker cannot read the arm64e.x1 stubs in the macOS 27 SDK.

The launcher resolves its module path from the Bazel-built distributions and runs on the selected JDK. Each guest test checks upstream output or diagnostics with both values of `sl.UseBytecode`. Tests extract the JNI attach library into Bazel's test temporary directory and fail if loading it fails. The `sl` launcher uses the interpreter. Use `sl_jit` to select the Labs JDK and run with the source-built Graal compiler on its upgrade module path.

```sh
bazelisk build --config=elide-processors @graal//compiler:GRAAL

bazelisk test --config=elide-processors @graal//compiler:sl_compilation_test
```

The compiler requires Labs JDK 25.0.5.1+0 with JVMCI 25.6-b27, as specified in the pinned Graal tree. JavaBuilder uses that JDK for projects importing concealed JVMCI APIs, with strict dependencies, annotation processing and ABI extraction. Four upstream compiler diagnostics are reported as warnings. The distribution merges generated service providers and option descriptors into its JPMS descriptor. The compiled guest test also verifies the file origin of the loaded compiler module.

The archive action consumes Truffle registration markers, filters documentation snippets using the suite pattern, and assembles the Java 9 and 21 overlays. The pinned mx includes a fix for repeated module descriptor rendering so both releases retain singleton qualified exports and service providers.

bazelisk build --config=elide-processors @graal//compiler:all_projects

Bazel lowers the native TARs and benchmark JARs from the pinned suite layout. The archive smoke test checks the packaged paths and runs the Fibonacci program extracted from `SL_BENCHMARKS`. Native archives contain the configured target's payload. The Linux configuration uses glibc.

## SubstrateVM builder

```sh
bazelisk build --config=elide-processors --config=labsjdk @graal//substratevm:SVM @graal//substratevm:support_distributions @graal//substratevm:test_distributions @graal//vm:VM_GRAALVM_SUPPORT
bazelisk test --config=elide-processors --config=labsjdk @graal//substratevm/... //graal:source_native_image_test
bazelisk build --config=elide-processors --config=labsjdk --output_groups=distribution @graal//substratevm:native-image.root
bazelisk test --config=source-native-image //graal:source_native_image_action_test @graal//substratevm:com.oracle.svm.with.space.test.com.oracle.svm.with.space.test.NativeImageResourceTest
bazelisk build --config=elide-processors --config=labsjdk @graal//substratevm:SVM_LLVM @graal//substratevm:SVM_GRAALVM_SUPPORT @graal//substratevm:JUNIT_SUPPORT
```

The builder uses the source-built Graal compiler and the relocated Espresso module. Bazel supplies option help files to javac's annotation processors through a declared source tree. The Native Image launcher uses the source-built driver, its generated JVM flags, the pinned Labs JDK and the Bazel C/C++ toolchain. The `source-native-image` profile registers this SDK as the `rules_graalvm` toolchain and selects Labs JDK 25 for both target and execution configurations. The action test exercises compilation as a Bazel build action. The SubstrateVM NFI and Truffle runtime support archives select individual inputs from Truffle’s LibFFI and header layouts. Native Image reads a symbol manifest next to each static library it can link. A Bazel action derives the manifests from `llvm-nm` and `llvm-objdump` output, as mx's static library symbol builders do: one for the SubstrateVM `libjvm.a` in `SVM_HOSTED_NATIVE`, and one per Labs JDK static archive in the launcher root. That root also contains the decoder-only `libzstd.a`, which images use to inflate compressed image-heap blobs, and the `zstd-jni` JAR that the builder uses to compress them.

The `com.oracle.svm.test` and `com.oracle.svm.truffle.test` classes run inside a Native Image under mx, so their per-class JVM labels are manual. On the pinned fork, `BundlePathMapTest` is also manual. Its class initializer loads every option descriptor, and `ShenandoahOptions` looks up `UnlockDiagnosticVMOptions` by its option name before that option's descriptor has been named, so the lookup fails when the Shenandoah descriptors load first (elide-dev/graal#257).

### Native unit tests

```sh
bazelisk test --config=elide-processors --config=labsjdk @graal//substratevm:native_unittest
```

`svm_native_unittest` follows `mx native-unittest`. The JUNIT_SUPPORT helper groups the selected classes by their `@NativeImageBuildArgs`. Each group becomes an `svmjunit` image, built with `--macro:junit` and the SubstrateVM test features, security providers, extra classpath directories and graph verification flags that the mx gate uses. The image then runs its classes with `--run-explicit`. The Native Image root contains the `junit` macro: its properties, JUNIT_SUPPORT, the mx JUnit harness, and JUnit and Hamcrest under the module names that mx gives them. The image classpath is `SVM_TESTS` without the distributions that the builder already provides.

`native_unittest` selects tests as the argument-less mx command does: the `SVM_TESTS` classes whose names contain `com.oracle.svm.test` or `com.oracle.svm.configure.test`, built into one image without the classes that need custom build arguments. At the pinned fork that is 129 classes and 332 test methods. mx ignores `URLProtocolTraceProcessorTest` there. `JCmdTest` is also left out: its `testVM` expects `jcmd VM.version` to name GraalVM, and the Native Image root is the Labs JDK rather than a GraalVM distribution. `GitHub1398` needs a multicast-capable network interface, which BuildBuddy's remote executors lack, so the test is tagged `no-remote-exec` and the `rbe` profile lets such actions run on the host. Use `svm_native_unittest` with explicit classes to build the custom groups.

### JVM unit tests

The hosted tests (`SVM_HOSTED_TESTS`, mx's `svm-invariants-tests` configuration), the standalone Pointsto tests (`STANDALONE_POINTSTO_TESTS`, `standalone-pointsto-unittest`) and the Graal tests use `svm_test_runner` launchers. They run on Labs JDK 25 with the source-built compiler on the upgrade module path. The launchers open JVMCI, compiler and GraalVM packages as mx's Graal unit test configuration does, and export the concealed packages that SubstrateVM projects require. Their classpath lists dependencies before the JARs that use them, as mx does, so ServiceLoader finds option descriptors in mx's order. `CheckSVMInvariants` receives every non-test SubstrateVM JAR and runs in the gate's `check_exclude_list` mode, with the named VM access modules on its module path. It is manual on the pinned fork: five reflection calls that the fork added, in `ZstdJni`, `ShenandoahFeature`, `MethodHandleInterpreterUtils` and `HostedPLTGOTConfiguration`, are missing from `VerifyReflectionUsage`'s exclude list. The Pointsto tests use the host VM access. The Espresso variant still needs qualification with the Espresso VM access implementation. `IsolatedSpeculationLogEncodingTest` is manual: no mx gate runs it, and on Labs JDK 25.0.5.1 JVMCI's speculation reason encoding differs from `IsolatedSpeculationLog`'s from the first byte.

### Platform-specific parts

- The LLVM backend (`SVM_LLVM`) compiles against the shadowed LLVM and JavaCPP JARs that mx downloads by URL. `graal/svm_inputs.json` pins them for Linux AMD64, Linux AArch64 and macOS AArch64, and a module extension fetches each one only when a build needs it. mx names the modules of the platform-specific JARs for the host it runs on, so `SVM_LLVM` requires them through a `select()`. The `llvm.bin.dir` property that mx passes to images using the backend is not set, and no test builds an image with the LLVM backend.
- `SVM_GRAALVM_SUPPORT` packages the debug helpers, `SVM_HOSTED_NATIVE`, the reporter library, zstd-jni, the reachability metadata schema and the skills. On macOS AArch64 it also contains the pinned standalone `ld64.lld`.
- `com.oracle.svm.native.jvm.windows` is compatible only with Windows targets. rules_mx pins no Windows Labs JDK, so building it also needs a Windows Labs JDK registered as `//tools:labs_runtime` for the JVM function fallbacks.

## Select the Graal source

`graal/source.json` pins the default archive: its URL, SHA-256 and strip prefix. The `graal` module extension in `graal/extensions.bzl` fetches that archive as `@graal` and applies the overlays generated for it. The Labs JDK pin in `mx/labsjdk.json` follows `labsjdk-ce-latest` in the same tree's `common.json`.

A consuming root module can select another archive. Generate overlays for it first, because the BUILD files list each suite's sources, projects and distributions:

```sh
tools/generate-graal --archive "$URL" --sha256 "$SHA256" --strip-prefix "$PREFIX" --output path/to/overlays
```

```starlark
graal = use_extension("@rules_mx//graal:extensions.bzl", "graal")
graal.source(
    urls = [URL],
    sha256 = SHA256,
    strip_prefix = PREFIX,
    patches = ["//path/to/overlays:sdk.patch", ...],  # source fixes and generated suite overlays
)
use_repo(graal, "graal")
```

Only the root module may declare `graal.source()`. Without it, the extension uses `graal/source.json` and the checked-in overlays. The external inputs (`shaded_inputs.json`, `libffi.json`, the LLVM, musl, HSDIS and VisualVM pins) are generated into the same output directory. The repository rules in this module still read the rules_mx copies, so a different source must match them or supply its own repositories.

To move this repository to a new revision, record the archive and regenerate everything in place:

```sh
tools/generate-graal --archive "$URL" --sha256 "$SHA256" --strip-prefix "$PREFIX" --pin
tools/generate-graal --check
```

## Extending the graph

The generator exports the selected suites from mx and runs Gazelle once across the suite graphs. SDK, Truffle, compiler, Regex, Tools and Espresso Shared select their roots from the resolved suite inventory. Suites with dynamically registered product configurations can select just their declared roots and still retain the resolved dependencies. Suite-specific settings bind custom native actions, artifacts and test launchers.

Run `tools/generate-graal --check` to reproduce the checked-in patches and pins from the archive in `graal/source.json`. The generator downloads and verifies the archive itself and runs mx discovery in a temporary tree that contains only the copied suites. Add suite or external dependency bindings to `tools/generate-graal` as needed, regenerate, and inspect the BUILD diff. To try a revision before changing the pin, pass a checkout path or `--archive` to the generator, with `--output` pointing outside `graal/`. Make the archive pin, patches and regression tests part of the same change.
